## Что это за проект

Сервис записи в салон красоты. Учебный фулстек-проект.

Клиент видит свободное время и бронирует его; у мастера — своё расписание,
управление графиком и аналитика; админ заводит услуги и мастеров.

Смысл проекта не в CRUD, а в двух вещах, которые и составляют настоящую
сложность систем бронирования:

1. **Корректный расчёт свободного времени** — интервалы переменной длины,
   графики, блокировки, часовые пояса.
2. **Защита от двойного бронирования при гонке** — между `SELECT` и `INSERT`
   всегда есть окно, в которое проскакивает второй клиент.

Полный план: `~/.claude/plans/imperative-waddling-haven.md`

```bash

cp .env.example .env      # если .env ещё нет; секрет: openssl rand -base64 32
```

## Соглашение о коммитах

Conventional Commits: `type(scope): description`.

**Сообщения коммитов пишутся по-английски** — заголовок и тело.
Комментарии в коде, документация и этот файл остаются на русском.

Типы: `feat` — новая функциональность, `fix` — исправление бага,
`refactor` — изменение кода без изменения поведения, `perf` —
производительность, `docs` — документация, `test` — тесты, `style` —
форматирование, `build` — сборка и зависимости, `ci` — CI/CD,
`chore` — технические изменения.

В теле коммита объяснять **почему**, а не что: «что» видно из диффа.

## Принятые решения

Пересматривать их можно, но осознанно — у каждого есть причина.

| Решение | Почему |
|---|---|
| Один салон, не маркетплейс | Модель данных остаётся читаемой, но все интересные задачи сохраняются |
| Роли CLIENT / MASTER / ADMIN | Три разных интерфейса — хорошая практика по авторизации |
| Длительность берётся от услуги | Интервалы переменной длины — суть задачи; фиксированные слоты сделали бы её тривиальной |
| Next.js как монолит | Знакомый стек, время уходит на предметную логику, а не на инфраструктуру |
| PostgreSQL, а не MySQL/SQLite | `EXCLUDE` + `tstzrange` есть только здесь. Это и есть причина выбора |
| Radix, но НЕ тема shadcn | Доступность из коробки, при этом свой визуальный язык |
| Цена — `Int` в копейках | Дробные типы для денег дают ошибки округления |
| `priceKopecksAtBooking` дублируется | Изменение прайса не должно задним числом менять выручку за прошлый месяц |
| `endsAt` хранится, а не вычисляется | `EXCLUDE`-констрейнт не может заглянуть в таблицу услуг за длительностью |
| `role` — `String`, а не enum | Так её создаёт Better Auth; целостность стережёт `CHECK`-констрейнт |
| Сетка привязана к началу смены | Иначе после записи, закончившейся в 9:50, предлагается «10:20» |
| Сид спрашивает время у `computeAvailableSlots` | Руками расставленные часы рано или поздно наложились бы друг на друга или на обед, и сид упал бы на `EXCLUDE`. Так он не может нарушить констрейнт в принципе, а домен проверяется на живой базе при каждом запуске |
| Пользователей сида создаёт `auth.api.signUpEmail` | `prisma.user.create` не создаёт запись в `account` с хешем пароля: учётка была бы в базе, но войти под ней нельзя. Роль дописывается вторым запросом — у поля `role` стоит `input: false` |
| Дата дня — в адресе (`?date=`), не в состоянии | Переключение дней работает без JS, ссылкой на день можно поделиться, «назад» ведёт куда ожидается |
| Гражданская дата — строка `YYYY-MM-DD`, а не `Date` | У «9 сентября» нет часового пояса. `Date` со скрытым UTC-смещением незаметно подменяет понятие «день» |
| Лента задаёт `--from` и `--len`, пиксели считает CSS | Масштаб (включая мобильный) меняется в одном месте, а в компонентах не заводятся размеры |
| Формы входа — Server Action, ошибки через `?error=` | Форма остаётся обычной HTML-формой и работает без JavaScript. Проверено: сабмит без JS даёт 303 и куку сессии |
| Иерархии ролей нет | ADMIN не «старше» MASTER и в кабинет мастера сам собой не попадает: там чужие записи и чужая выручка. Нужен доступ — роль выписывается в списке явно |
| `parseRole` возвращает `null`, а не бросает | `role` в базе — `String`. Падение страницы на неизвестной роли — отказ в обслуживании вместо честного «доступа нет» |
| Выход — форма, а не ссылка | По GET состояние менять нельзя: ссылку дёрнет префетч или ускоритель браузера, и человек разлогинится сам собой |
| Интеграционные тесты — база `salon_test` в том же контейнере | Testcontainers дали бы изоляцию, но добавили бы зависимость, десятки секунд на старт и второй способ получить базу. Здесь достаточно соседней базы: `TRUNCATE` между тестами, один поток |
| Слот в ленте высотой в шаг сетки, а не в длительность | Слоты идут каждые 30 минут: при часовой услуге они перекрывали бы друг друга. Длительность лента и так показывает блоками занятого времени |
| При взаимоблокировке — один повтор, а не сразу отказ | `40001`/`40P01` означают лишь, что двое писали одновременно; кто победил, ещё неизвестно. Ко второй попытке чужая транзакция завершилась, и ответ определённый |
| `zod` поставлен диапазоном `^4.6.0` | Совпадает с требованием better-auth (`^4.5.4`), поэтому npm свёл дерево к одной копии. Своя копия рядом с копией библиотеки — источник «типы не совпадают» на ровном месте |

### Дизайн: направление «Хронограф»

Расписание — вертикальная лента дня, **высота блока пропорциональна
длительности**: окрашивание на 180 минут втрое выше стрижки на 60.
Масштаб: 1 минута = 1.2px (на мобильном 0.9), задан переменной
`--ribbon-px-per-min`.

Это единственное место, где дизайн громкий. Всё остальное — тихое.

Токены живут **только** в `src/app/globals.css`. Хардкод цвета или кегля
в компоненте — ошибка ревью.

Чего сознательно не делаем: кремовый фон с серифом и терракотовым акцентом
(самый шаблонный вариант для бьюти-салона), разряженные ALL-CAPS-надзаголовки,
одинаковые карточки с одним радиусом и мягкой тенью, `→` в конце кнопок,
появление секций при скролле.

**Радиус кодирует роль элемента:** блоки ленты — 4px, кнопки — таблетка,
аватары — круг. Единый радиус на всём читается как шаблон.

## Грабли, на которые уже наступили

Каждая из них стоила времени. Не наступать повторно.

**Prisma: тег `latest` указывает на release candidate.**
`npm i prisma` ставит `8.0.0-rc.13`; стабильная версия спрятана под тегом
`prev`. При этом CLI и `@prisma/client` встали разных мажорных версий.
Обе части закреплены на `7.10.0`. При обновлении проверять `npm view prisma dist-tags`.

**Prisma 7 сильно отличается от 6.**
Генератор называется `prisma-client` (не `prisma-client-js`), требует явный
`output`, клиент генерируется в `src/generated/prisma` и импортируется оттуда,
а не из `@prisma/client`. `url` в `datasource` больше не поддерживается —
строка подключения в `prisma.config.ts`. Подключение идёт через
драйвер-адаптер `@prisma/adapter-pg`. `.env` Prisma сама не читает, нужен
`import "dotenv/config"`.

**Bricolage Grotesque не имеет кириллицы.**
Заголовки на русском молча свалились бы в запасной шрифт. Заменён на
**Unbounded**. При выборе любого шрифта сначала проверять `subsets` в
`node_modules/next/dist/compiled/@next/font/dist/google/index.d.ts`.

**better-auth конфликтует с vitest 5.**
Объявляет `peerOptional vitest ^2||^3||^4`. Vitest опущен до 4 — для наших
тестов разница нулевая, зато дерево сходится без `--legacy-peer-deps`.
Флаг не использовать: он войдёт в привычку и однажды скроет настоящий конфликт.

**`create-next-app` прописал `@types/node@^20` при Node 24.**
Типы отставали от рантайма. Подняты до `^24`.

**Имя папки `Booking` с заглавной буквы.**
npm запрещает заглавные в имени пакета, `create-next-app` отказывается
работать. Проект собран во временной папке и перенесён. Имя пакета —
`salon-booking`.

**Prisma 7 не поднимает код PostgreSQL наверх.**
Пересечение приезжает как `PrismaClientKnownRequestError` с кодом
**`P2039`**, а настоящий `23P01` лежит в `meta.driverAdapterError.cause`.
Проверять `error.code === "23P01"` бесполезно — такого не бывает.
Форма ошибки снята с живой базы, разбор — в `src/lib/db-errors.ts`.

**Гонка отвечает не только `23P01`, но и взаимоблокировкой.**
При настоящей одновременной вставке PostgreSQL иногда отдаёт `40001`
(Prisma переводит его в свой `P2034`) или `40P01` (остаётся `P2039`).
Без обработки это вылезало наружу пятисотой примерно раз из пяти
прогонов теста на гонку. Лечится одним повтором.

**Тест на гонку нельзя писать со строгим ожиданием.**
Проигравший получает то `SLOT_TAKEN`, то `NOT_AVAILABLE` — зависит от
того, кто первым дошёл до базы. Инвариант («ровно одна запись»)
проверяется отдельно от пути через констрейнт, а тот воспроизводится
детерминированно: незафиксированная транзакция держит диапазон, вторая
попытка упирается в него и ждёт коммита.

**`redirect()` внутри `try` — съеденный редирект.**
`redirect()` работает через исключение, которое ловит Next. Свой
`catch` вокруг него превращает штатный переход в «неизвестную ошибку».
В Server Action сначала запоминаем исход флагом, редирект — после `catch`.

**Из файла с `"use server"` можно экспортировать только async-функции.**
Обычная функция-помощник рядом с Server Action ломает сборку.
`safeNext` уехал в `src/lib/safe-next.ts`.

**Better Auth отвергает POST без заголовка `Origin`.**
`curl` на `/api/auth/sign-out` отвечает 403, и это не поломка, а CSRF-защита.
С `-H "Origin: http://localhost:3000"` тот же запрос проходит.

**`Intl` разделяет разряды неразрывными пробелами (U+00A0).**
Тест с обычным пробелом падает с сообщением «ожидалось 3 500 ₽,
получено 3 500 ₽» — разница невидима. В ожиданиях пробел записан
escape-последовательностью с комментарием.

**Прибавлять минуты к полуночи — ошибка в день перевода часов.**
`полночь + 600 минут` в сутки длиной 23 или 25 часов даёт 09:00 или 11:00
вместо 10:00. Часы и минуты передаются конструктору `TZDate` сразу,
и на это есть тест с Берлином (в Москве DST нет — на ней баг не всплыл бы).

**`.gitignore` от Next игнорирует `.env*` целиком**, включая `.env.example`.
Добавлено исключение `!.env.example`.

**CLI `@better-auth/cli` помечен в npm как устаревший** и приезжает версии
1.4.21 при библиотеке 1.7.3. Схему он сгенерировал корректно, но дальше
`prisma/schema.prisma` ведём руками.

## Ручной SQL в миграции — не потерять

В конце `prisma/migrations/*_init/migration.sql` дописаны ограничения,
которые Prisma описать не умеет. **При пересоздании миграций их надо
перенести руками.**

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "appointment"
  ADD CONSTRAINT "appointment_no_overlap"
  EXCLUDE USING gist (
    "masterId" WITH =,
    tstzrange("startsAt", "endsAt", '[)') WITH &&
  )
  WHERE ("status" <> 'CANCELLED');
```

Три детали, каждую из которых легко упустить:

- `'[)'` — полуоткрытый интервал. Записи 10:00–11:00 и 11:00–12:00 **не**
  конфликтуют. С `'[]'` конфликтовали бы.
- `WHERE ("status" <> 'CANCELLED')` — частичный констрейнт. Без него
  отменённая запись продолжала бы занимать время.
- `btree_gist` — чтобы в GiST-индекс лёг обычный `"masterId" WITH =`.

Плюс `CHECK`-констрейнты: допустимые роли, `startsAt < endsAt` для записей
и блокировок, границы рабочих часов.

Сервисный слой должен ловить код ошибки PostgreSQL **`23P01`**
(`exclusion_violation`) и превращать его во внятное «это время только что
заняли, выберите другое».

### Проверено на живой базе

Все четыре правила подтверждены прямыми запросами:

- пересекающаяся запись — отвергнута;
- смежная запись встык — прошла;
- после отмены время освободилось;
- роль `SUPERADMIN` — отвергнута.

## Инварианты, которые нельзя нарушать

- **Server Action не содержит бизнес-логики.** Только: проверка сессии и роли,
  валидация через Zod, вызов сервиса, `revalidatePath`.
- **`src/domain/` не знает про Prisma и про Next.** Только чистые функции.
  Поэтому они и тестируются за миллисекунды.
- **`computeAvailableSlots` принимает `now` параметром.** Никакого
  `new Date()` внутри — иначе тесты начнут зависеть от времени запуска.
- **Слоты в ленте — настоящие `<button>` в списке, не раскрашенные `div`.**
  Визуально это лента, но для клавиатуры и скринридера — обычный перечень
  времени. Проверка: пройти весь путь бронирования без мыши.
- **Всё время в БД — UTC (`timestamptz`).** Рабочие часы хранятся как минуты
  от полуночи по времени салона (`SALON_TIMEZONE`), и конвертация происходит
  ровно в одном месте. Иначе всё работает до перехода на летнее время.

Лента сознательно сделана только на просмотр. Слотов-кнопок в ней пока нет:
без выбранной услуги неизвестна длительность, а значит и слоты. Появятся
вместе с бронированием — и сразу как `<button>` в списке, по инварианту.
